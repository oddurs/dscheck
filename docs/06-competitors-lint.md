# Competitor analysis: `dslint` (off-system value linter)

*Status: research, 2026-08-23. Companion to [05-concept-lint.md](05-concept-lint.md); goes deeper than [01 §4 Linting](01-tooling-landscape.md). Stats verified 2026-08-23 via npm registry, api.npmjs.org (weekly unless noted), and GitHub API.*

## TL;DR

Nobody ships a **generic, token-source-aware** linter. Every existing tool either (a) enforces "use *a* variable" without knowing which variables are yours, (b) is hard-wired to one org's token package (Atlassian, Primer, Carbon, MetaMask, Shopify†), (c) lints the **token file** instead of the code that uses it (Terrazzo, Style Dictionary), or (d) covers exactly one surface (Tailwind classes *or* CSS *or* Panda). The one tool that shares dslint's framing — nearest-token suggestions + new-debt-only PR gate — is a month-old zero-star regex CLI ([@hyuga/tokenlint](https://github.com/hyuga611/tokenlint)), colors-only. The biggest threat is real and recent: **Tailwind shipped canonical-class suggestions in core** (v4.1.15, [PR #19059](https://github.com/tailwindlabs/tailwindcss/pull/19059)), surfaced by IntelliSense and eslint-plugin-better-tailwindcss — that covers dslint's `no-arbitrary-class` for Tailwind-only shops.

## 2. Per-competitor notes

### 2.1 Generic stylelint layer (the incumbent "80% solution")

**stylelint-declaration-strict-value** — [repo](https://github.com/AndyOGo/stylelint-declaration-strict-value) · 144★ · MIT · v1.11.1, published 2026-08-20 · **594k dl/wk**.
The de-facto standard. Forces configured properties (e.g. `/color/`, `z-index`) to use a variable, function, or keyword; `expandShorthand` handles `border` etc.; `autoFixFunc` lets *you* write a value→token mapping by hand. Critically it has **no notion of your token set**: any `var(--anything)` or SCSS `$anything` passes, so a hallucinated `var(--color-primary-500)` is invisible. CSS-in-JS support is an explicit wontfix ([#134](https://github.com/AndyOGo/stylelint-declaration-strict-value/issues/134): "out of the scope of this plugin"). No suggestions, no baseline, no Tailwind. Its 594k/wk proves the demand for exactly this rule shape; its gaps define dslint's `no-raw-*` + `no-unknown-token` pair. The DIY endgame is visible in [Michael Mang's blog](https://www.michaelmang.dev/blog/linting-design-tokens-with-stylelint/): a bespoke stylelint rule that loads token JSON and suggests nearest matches — people hand-roll dslint today.

**stylelint-value-no-unknown-custom-properties** — [repo](https://github.com/csstools/stylelint-value-no-unknown-custom-properties) · 76★ · CC0-1.0 · v6.1.1, 2026-01 · **259k dl/wk** (csstools).
The closest existing thing to `no-unknown-token`: flags `var(--x)` when `--x` isn't defined in the file or in [`importFrom`](https://github.com/csstools/stylelint-value-no-unknown-custom-properties#importfrom) sources (CSS/JS/JSON with a `custom-properties` key — a proprietary shape, not DTCG). No Tailwind `@theme` awareness, no nearest-name suggestion for typos, CSS-only, no fix. Proves the "unknown var" rule has an audience but stops at declaration-side CSS.

**Stylelint core DIY** — [`declaration-property-value-allowed-list`](https://stylelint.io/user-guide/rules/declaration-property-value-allowed-list/), `declaration-property-value-disallowed-list`, [`color-no-hex`](https://stylelint.io/user-guide/rules/color-no-hex/), `color-named`, `unit-allowed-list`, `custom-property-pattern`.
You can ban hex and whitelist `var(--space-\d)` by regex today with zero plugins. But the allowed list is a hand-maintained regex that silently drifts from the real token file, there are no suggestions, and nothing reads a token source. Relevant platform facts: stylelint **removed built-in CSS-in-JS** processing in v15 (community `postcss-styled-syntax` covers styled-components/emotion template literals only); Vue/Svelte/HTML `<style>` work via `postcss-html`; stylelint 16.25.0 (2025-10) shipped **experimental bulk suppressions** (`--suppress`, same per-file/per-rule count format as ESLint); there is **no maintained SARIF formatter** ([stylelint-sarif-formatter](https://www.npmjs.com/package/stylelint-sarif-formatter) is stale since 2022) — a gap dslint's stylelint adapter can fill.

**Format references** (not competitors): [stylelint-use-logical](https://github.com/csstools/stylelint-use-logical) (243k/wk, CC0) — clean prop→prop fix model; [stylelint-no-unsupported-browser-features](https://github.com/ismay/stylelint-no-unsupported-browser-features) (453★, 391k/wk) — the best precedent for dslint's shape: a stylelint rule whose allowed set comes from an **external project-level source of truth** (browserslist ≈ token file).

### 2.2 Org-specific plugins (the pattern dslint generalises)

**@atlaskit/eslint-plugin-design-system** (Atlassian) — [npm](https://www.npmjs.com/package/@atlaskit/eslint-plugin-design-system) · Apache-2.0 · v16.11.0, 2026-08-20 · **5,984 dl/wk** · monorepo [atlassian-frontend-mirror](https://bitbucket.org/atlassian/atlassian-frontend/src/master/).
The most complete implementation of dslint's idea anywhere — 60+ rules including `ensure-design-token-usage` (recommended, fixable, **with suggestions** — raw colors in Compiled/emotion/styled-components/xcss/inline styles get candidate `@atlaskit/tokens` replacements), `no-unsafe-design-token-usage`, `no-deprecated-design-token-usage` (autofix along Atlassian's migration map), `use-tokens-space/typography/motion/shape`. Companion [@atlaskit/stylelint-design-system](https://www.npmjs.com/package/@atlaskit/stylelint-design-system) (1,719/wk). **Hard-wired to `@atlaskit/tokens`** — the token list is imported from their package, not configurable; unusable for any other DS. This is dslint's existence proof and quality bar: Atlassian spent years building it because nothing generic existed.

**@primer/stylelint-config** (GitHub) — [repo](https://github.com/primer/stylelint-config) · 208★ · MIT · v13.6.0, 2026-08-17 · **6,859 dl/wk**.
Ships seven custom plugins (`primer/colors`, `spacing`, `typography`, `borders`, `box-shadow`, `responsive-widths`, `no-display-colors`) that load the allowed set **from `@primer/primitives` token JSON at lint time** (`dist/styleLint/*.json`, DTCG-style `$value`) — the closest architecture to dslint's resolver, including per-role property maps (fg/bg/border color categories). Fix support where a replacement map exists (exact matches). But the source path, roles, and categories are hard-coded to Primer's package layout; nothing is pluggable. eslint side: [eslint-plugin-primer-react](https://github.com/primer/eslint-plugin-primer-react) (14★, 20,253/wk) with `no-system-props`, deprecated-color CSS-var migrations in `sx`.

**stylelint-plugin-carbon-tokens** (IBM) — [repo](https://github.com/carbon-design-system/stylelint-plugin-carbon-tokens) · 10★ · Apache-2.0 · v5.0.6, 2026-06 · **2,530 dl/wk** · pushed 2026-08-22.
The most technically thorough org plugin: five token categories (theme/layer/layout/type/motion), validates both SCSS `$spacing-05` and `var(--cds-spacing-05)`, handles shorthands (`transition`, `animation`, `font`, `border`, `outline`), `calc()`/`rgba()` wrapping, autofix, three strictness presets. Allowed set = Carbon v11 packages, hard-wired. TypeScript rewrite in 2025-26 — actively invested, still single-DS.

**@shopify/stylelint-polaris** — [npm](https://www.npmjs.com/package/@shopify/stylelint-polaris) · MIT · v16.0.7 · 5,943 dl/wk · **effectively EOL**: the [Polaris monorepo](https://github.com/Shopify/polaris) (6,173★) was archived 2026-08-11 after the Web Components pivot. 40+ token-pushing rules die with it; the replacement components got no linter. A cautionary tale for coupling rules to one component library.

**@metamask/eslint-plugin-design-tokens** — [repo](https://github.com/MetaMask/eslint-plugin-design-tokens) · 3★ · MIT/Apache · v1.1.1 · **57,273 dl/wk** (MetaMask's own CI + forks — stars vs downloads shows org plugins get used without community). Three rules: [`color-no-hex`](https://github.com/MetaMask/eslint-plugin-design-tokens/blob/main/docs/rules/color-no-hex.md), `prefer-theme-color-classnames`, `no-deprecated-classnames` — JSX + Tailwind classname strings, allowed names hard-coded to MetaMask's theme.

**Mozilla `no-base-design-tokens`** — [docs](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/no-base-design-tokens.html). In-tree only (not on npm). Notable for the **role** idea: base tokens are banned in favour of semantic ones — dslint's `token-role` rule generalises this.

**@pandacss/eslint-plugin** — [repo](https://github.com/chakra-ui/eslint-plugin-panda) · 99★ · MIT · v0.3.2, 2026-08-15 · **31,348 dl/wk**.
The only *framework* plugin that reads the user's own token config: `no-hardcoded-color` and `no-invalid-token-paths` resolve against `panda.config` (via `configPath`), and [`no-escape-hatch`](https://github.com/chakra-ui/eslint-plugin-panda/blob/main/docs/rules/no-escape-hatch.md) bans `[raw]` escapes. But it only lints Panda's own authoring APIs (`css()`, styled props) — plain CSS, Tailwind, other CSS-in-JS are out of scope by design. No nearest-token, no baseline. If you're all-in on Panda you don't need dslint's JS surface; almost nobody is.

**Gaps in the org pattern**: Chakra has no token linter (community [eslint-plugin-chakra-ui](https://www.npmjs.com/package/eslint-plugin-chakra-ui) v0.12.0, 2025-01, is props-hygiene); Salt (`@salt-ds`) ships none (no `@salt-ds/eslint-plugin` on npm); vanilla-extract has none ([eslint-plugin-vanilla-extract](https://www.npmjs.com/package/eslint-plugin-vanilla-extract) v0.1.0, dead 2022). Generic npm names: **`eslint-plugin-design-tokens` is empty** (a prior package was unpublished from npm in 2024 — the generic niche has literally been vacated); `eslint-plugin-design-system` is squatted by an unrelated v1.0.1 from 2022 (26 dl/wk).

### 2.3 Tailwind ecosystem (the crowded surface)

**eslint-plugin-tailwindcss** — [repo](https://github.com/francoismassart/eslint-plugin-tailwindcss) · 2,073★ · MIT · v4.4.0, 2026-08-21 · **1.65M dl/wk**.
Rebuilt for Tailwind v4 (theme read from the CSS `entryPoint`). Three relevant rules: `no-arbitrary-value` (blanket ban, **not in recommended** — too blunt for real codebases), `no-custom-classname` (recommended; known [false-positive pain](https://amanhimself.dev/blog/resolving-custom-tailwind-classname-eslint-warning/) with plugin-generated classes), and `no-unnecessary-arbitrary-value` (recommended, fixable): flags `p-[16px]` when `p-4` exists — i.e. **exact-match nearest-token for Tailwind only**. No distance-based suggestion (`p-[13px]` passes), no CSS, no baseline.

**eslint-plugin-better-tailwindcss** — [repo](https://github.com/schoero/eslint-plugin-better-tailwindcss) · 826★ · MIT · v4.7.0, 2026-07 · **851k dl/wk**.
The stronger v4-native option: correctness rules `no-unknown-classes`, `no-conflicting-classes`, `no-restricted-classes`, and [`enforce-canonical-classes`](https://github.com/schoero/eslint-plugin-better-tailwindcss/blob/main/docs/rules/enforce-canonical-classes.md) — which wraps **Tailwind core's own canonical-suggestion engine** ([tailwindcss PR #19059](https://github.com/tailwindlabs/tailwindcss/pull/19059), `^4.1.15`): arbitrary values with a predefined equivalent are rewritten to the theme class, including px↔rem conversion via `rootFontSize`. Wide surface: JSX, Vue, Svelte, Astro, HTML, template literals, configurable callees (`clsx`/`cva`/`cn`). Still Tailwind-classes-only: no CSS declarations, no inline styles, no non-exact distance suggestions, no baseline, no escape-hatch trend.

**Tailwind IntelliSense / @tailwindcss/language-server** — [repo](https://github.com/tailwindlabs/tailwindcss-intellisense) · 3,463★ · v0.16.0 · 72,415 dl/wk.
**Already flags arbitrary values with canonical equivalents, on by default**: "Add diagnostic to suggest canonical classes by default" landed in v0.14.28 ([PR #1475](https://github.com/tailwindlabs/tailwindcss-intellisense/pull/1475)), px/rem-aware matching in v0.14.29 ([PR #1476](https://github.com/tailwindlabs/tailwindcss-intellisense/pull/1476)), controlled by `tailwindCSS.lint.suggestCanonicalClasses`. Editor-only — no official headless/CI runner — but first-party and zero-config. This is the strongest evidence that Tailwind Labs considers off-theme arbitrary values a linting concern; expect them to keep going.

**Runners**: oxlint has no native Tailwind rules (its route is ESLint-compatible [JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins)); Biome only sorts classes ([useSortedClasses](https://biomejs.dev/linter/rules/use-sorted-classes/)). [tailwind-csstree](https://www.npmjs.com/package/tailwind-csstree) (857k/wk, Apache-2.0) is parsing infrastructure (used by the lint plugins), not a linter. prettier-plugin-tailwindcss is ordering only. Net: dslint's biome/oxlint adapter story matches where those runners are heading (ESLint-plugin compat), and no runner owns token-awareness.

### 2.4 Token-toolchain lint (they lint the tokens, not the code)

**Terrazzo** — [repo](https://github.com/terrazzoapp/terrazzo) · 446★ · MIT · @terrazzo/cli v2.7.1, 2026-08 · **69,161 dl/wk**.
Has a real [lint plugin system](https://terrazzo.app/docs/linting/): `core/valid-*` per DTCG type, `core/consistent-naming`, `core/duplicate-values`, `core/required-modes`, `core/colorspace`, `core/max-gamut`, plus `a11y/min-contrast` / `a11y/min-font-size`. **Every rule validates the token file itself; none examines CSS/JSX/application code** (confirmed against the docs 2026-08-23). Terrazzo is dslint's natural *complement* (and its DTCG parser is a candidate dependency) — but it owns the "lint" word in the DTCG community and could expand toward code.

**Style Dictionary** — [repo](https://github.com/style-dictionary/style-dictionary) · 4,779★ · Apache-2.0 · v5.5.2 · **2.05M dl/wk**. Validates token files/references at build time (DTCG-aware since v4); `sd lint`-style code checking doesn't exist. Same story for **Tokens Studio** (in-plugin schema validation) and the retired cobalt-ui (→ Terrazzo).

### 2.5 The generic-CLI long tail (spiritual competitors)

**@hyuga/tokenlint** — [repo](https://github.com/hyuga611/tokenlint) · 0★ · MIT · v0.5.0; created 2026-07-22, last publish 2026-08-18 · 487 dl/wk.
A month old, one author, zero dependencies, regex-based — and the **closest concept match found anywhere**: counts hardcoded colors in CSS *and* Tailwind arbitrary color classes, treats `--color-*` custom properties as the token palette, gives a **nearest-token suggestion by perceptual distance**, and gates PRs on **net-new debt** (`--since` / `--max-new`, GitHub Action) with coverage badges and an HTML scorecard. Marketed explicitly at AI-agent repos. Honest limitations in its own README: colors only, no named colors, no SCSS vars, no semantic Tailwind classes, no token file formats, no eslint/stylelint integration, no fix, no SARIF, no editor squiggles. Validation of the thesis (independent invention, agent-drift framing) more than a threat — but it got there first publicly, so ship before it grows surfaces.

**Name-collision squatters, not competitors**: npm [`dslint`](https://www.npmjs.com/package/dslint) is vutran's dead 2019 Figma-file linter (v0.0.2, last publish 2022, ~6 dl/wk, [repo](https://github.com/vutran/dslint) 44★ last pushed 2020); npm [`design-lint`](https://www.npmjs.com/package/design-lint) is an unrelated v0.0.8 AI-review stub (2025, ~35 dl/month); the well-known [destefanis/design-lint](https://github.com/destefanis/design-lint) (518★) is the Figma plugin covered in 01. No `drift-guard` design-tooling exists on npm or GitHub (the name is used by unrelated GitOps/ML projects).

**Adoption-metrics adjacents**: [Project Wallace css-analyzer](https://github.com/projectwallace/css-analyzer) (364★, 9.5k/wk) extracts "design tokens" *descriptively* from shipped CSS (unique colors/spacing counts); its `css-design-tokens` package even emits DTCG from CSS (note: EUPL-1.2 copyleft) — but it never validates against *your* token set. The new [@projectwallace/stylelint-plugin](https://www.npmjs.com/package/@projectwallace/stylelint-plugin) (v0.7.0, Aug 2026, ~1k/wk) has a "design-tokens" preset that is all **uniqueness thresholds** (`max-unique-colors` style) — a ratchet on entropy, not conformance to a source; its dead predecessor [constyble](https://www.npmjs.com/package/constyble) (2022, 76/wk) had the same idea plus crude color allowlists — the closest prior art for "debt as a number". [react-scanner](https://github.com/moroshko/react-scanner) (657★, 314k/wk) counts component/prop usage, value-blind. These confirm "% off-system over time" is currently answered by *counting uniques*, never by *diffing against the token source*.

### 2.6 Baseline / ratchet and CI formats (what dslint must be compatible with)

Condensed from the dedicated research pass (2026-08-23):

- **ESLint core bulk suppressions** since [v9.24.0](https://eslint.org/docs/latest/use/suppressions) (2025-04): `eslint-suppressions.json` stores per-file/per-rule violation *counts*; `--suppress-all`, `--suppress-rule`, `--prune-suppressions`. Works for plugin rules → **dslint's eslint adapter gets baseline for free**; error-severity only, and a count-rise reports all violations in the file — dslint's own CLI baseline can be finer-grained (fingerprints) while staying philosophy-compatible.
- **stylelint 16.25.0** (2025-10) shipped the same experimental mechanism (`--suppress`, same count format); no Node API yet. **oxlint** v1.64+ has ESLint-compatible suppressions; **Biome** uses bulk inline `// biome-ignore` comments (diff-heavy).
- **Betterer** ([repo](https://github.com/phenomnomnominal/betterer), 632★, ~70k/wk but last stable release 2022, alpha since) is the cautionary tale: per-line-hash results files cause merge churn ([#1253](https://github.com/phenomnomnominal/betterer/issues/1253)). The ecosystem converged on count-based sidecars instead.
- **SARIF**: [@microsoft/eslint-formatter-sarif](https://www.npmjs.com/package/@microsoft/eslint-formatter-sarif) at **1.55M dl/wk** is the de-facto CI bridge; **no maintained stylelint SARIF formatter exists** — dslint can be the one. GitHub Code Scanning's `partialFingerprints` give "new findings only" on PRs for free if dslint emits stable fingerprints. reviewdog (sarif/rdjson), [eslint-plugin-diff](https://www.npmjs.com/package/eslint-plugin-diff) (264k/wk) and lint-staged (28M/wk) all work unchanged with host-linter adapters.

### 2.7 AI-era conformance and commercial platforms (checked: none validate)

- **Figma Dev Mode MCP** ([guide](https://help.figma.com/hc/en-us/articles/32132100833559-Guide-to-the-Dev-Mode-MCP-Server)): tools provide *context* (`get_code`, `get_design_context`, `get_variable_defs`, `create_design_system_rules`) — rules files steer the model up front; **no tool validates or audits generated code** against variables. Same instruct-not-verify pattern across Superdesign, v0/shadcn registry (schema validation of registry JSON only), and Builder.io-style "enforce your design system" claims, which are prompt-side.
- **Supernova** ([product](https://www.supernova.io/)): token management, docs, pipelines, and "Context Intelligence" MCP endpoints for agents — explicitly the *feed-the-agent* half. Its adoption dashboard (May 2026) is Enterprise-only, React-only, and counts **component/prop usage**, not token conformance; the MCP is read-only queries, no validation ([@supernovaio/cli](https://www.npmjs.com/package/@supernovaio/cli) ~7.9k/wk). **zeroheight** *markets* "hardcoded values / drift" detection but documents no collection mechanism — marketing aspiration, Enterprise-gated analytics. **Knapsack**: no code scanning at all.
- **Omlet** ([omlet.dev](https://omlet.dev/), by Zeplin): was the real commercial adjacency — CLI-scanned React/RN **component and prop adoption** dashboards ([@omlet/cli](https://www.npmjs.com/package/@omlet/cli) ~134k/wk). Value-blind: no hardcoded-color/spacing detection, no token awareness. Telling coda: Omlet **went open source in Apr 2026 and sunset the hosted product** — component-adoption analytics alone couldn't sustain a business. The graveyard agrees: Backlight (dead June 2025), Specify (shut down), radius-tracker (dormant), cssstats (unmaintained). Standalone DS-analytics SaaS economics are proven bad; lint-plugin distribution (594k–1.65M dl/wk incumbents above) is the validated channel.
- Storybook's token addons (e.g. storybook-design-token) *display* tokens; no validation. No "design system conformance checker for AI output" product was found in any search pass — the phrase currently has no owner.

## 3. What nobody does (the whitespace, with evidence)

1. **Read a standard token source and enforce it generically.** Every value-enforcing linter is either token-blind (declaration-strict-value accepts any `var()`) or hard-wired (Atlaskit→`@atlaskit/tokens`, Primer→`@primer/primitives`, Carbon→Carbon v11, MetaMask→their theme, Mozilla→in-tree). Zero tools accept "here is my DTCG file / `@theme` block, lint against it." Terrazzo — the DTCG linter — confirms in its docs that no rule touches application code.
2. **One allowed-set across surfaces.** CSS linting (stylelint world), Tailwind class linting (eslint plugins), and CSS-in-JS linting (Panda only) are three disjoint ecosystems with three different theme readers. Nobody diffs a JSX `style={{gap: 14}}` and a `.css` declaration against the same source. stylelint's CSS-in-JS story regressed (v15 removal; strict-value wontfix); the Tailwind plugins stop at class strings.
3. **Distance-based nearest-token suggestions.** The state of the art is *exact-match* rewriting (Tailwind canonical classes, `no-unnecessary-arbitrary-value`, Primer replacement maps). `p-[13px]` → "did you mean `p-3` (12px)?" and `#3b82f6` → "`--color-primary`, ΔE 0.4" exist only in a hand-rolled blog rule and a 0-star regex CLI. Atlassian's suggestion engine is the exception — locked to their tokens.
4. **Baseline/ratchet for design debt.** No design-system linter ships one (Atlaskit: no; Carbon: no; Tailwind plugins: no). Host-linter suppressions only just arrived (ESLint 9.24, stylelint 16.25 experimental) and no DS tool exploits them, let alone a cross-surface count with trend reporting.
5. **Escape hatches as data.** Panda *bans* `[raw]`; Shopify shipped a *bulk-disable inserter*; nobody reports suppressions/arbitrary-value counts over time. (Gap #11 from 01 still stands; only @hyuga/tokenlint's coverage badge gestures at it, colors-only.)
6. **SARIF for style linting.** 1.55M/wk proves SARIF demand on the eslint side; the stylelint side has had no maintained formatter since 2022.
7. **A validator in the agent loop.** Figma MCP, Supernova, v0, Superdesign all *instruct* the model; none *check* the output. "Post-generation token-violation lint" (03 §4.1) remains unbuilt by anyone, including the platforms best positioned to build it.

## 4. Where dslint would lose (honest threats)

1. **Tailwind Labs owns the Tailwind surface.** Canonical-class suggestions are in **core** (v4.1.15) and on-by-default in IntelliSense; better-tailwindcss already exposes them in CI with 851k/wk reach. For a Tailwind-v4-only shop, `no-arbitrary-class` + `no-unknown-classes` are solved today without dslint — and if Tailwind ships a first-class `--lint` CLI, that whole surface evaporates. dslint's Tailwind rule must be a thin conformance wrapper (ideally reusing Tailwind's own engine, as better-tailwindcss does), with the differentiation in *cross-surface unification, distance matching, and the trend report* — not in class parsing.
2. **"Good enough" stacking of incumbents.** declaration-strict-value (594k/wk) + value-no-unknown-custom-properties (259k/wk) + better-tailwindcss covers maybe 70% of the value at zero new-tool cost. dslint must win on the delta (token-source truth, suggestions, one config) and on setup time, or teams will keep stacking.
3. **Terrazzo expands one layer up.** It has the DTCG parser, the lint framework, the plugin system, the community mindshare, and 69k/wk. A `@terrazzo/plugin-code-usage` is a plausible 2027 move; dslint's moat is then only the surfaces + host-linter integration. (Mitigation: build on their parser, stay adapter-first, move fast on eslint/stylelint distribution they don't have.)
4. **Host-linter platform risk.** The eslint adapter needs type-aware-ish JSX analysis and Tailwind string extraction inside eslint's architecture; oxlint/Biome migration could strand a heavy eslint-plugin (mitigated by the shared-core design, but adapters aren't free). Stylelint's CSS-in-JS regression means dslint carries its own CSS-in-JS scanners — the hardest, least-shared code, against a fragmenting CSS-in-JS market (styled-components in maintenance mode since 2025).
5. **False-positive fatigue is how every predecessor died socially.** `no-custom-classname`'s reputation ([teams disable it](https://amanhimself.dev/blog/resolving-custom-tailwind-classname-eslint-warning/)), Shopify shipping a bulk-disabler, Atlaskit's config-heavy onboarding. One noisy default (e.g. flagging one-off marketing pages) and dslint is "that annoying linter". Conservative defaults + baseline aren't features, they're survival.
6. **Org-plugin gravity.** The biggest design systems (the likeliest paying users) already sank cost into bespoke plugins with migration maps dslint can't know (deprecated→new token graphs). They adopt dslint only if it imports their token metadata cheaply.
7. **Name risk is minor but real**: `dslint` on npm is squatted by a dead package (transferable via [npm dispute](https://docs.npmjs.com/policies/disputes) or publish under `@dslint/*`), and `dslint`/`dslinter` already mean other things on GitHub (Kotlin-DSL android linter 71★, pylint ML linter).

## 5. Positioning

**For teams whose UI is increasingly written by agents, dslint is the linter that knows *your* design system: it reads the token source you already have — DTCG JSON, Tailwind `@theme`, or CSS custom properties — and turns every off-system value in CSS, JSX, CSS-in-JS, or Tailwind classes into an ordinary eslint/stylelint finding with the nearest on-system token attached. Unlike declaration-strict-value it knows which variables are real; unlike Atlaskit/Primer/Carbon's plugins it works with *your* tokens; unlike Terrazzo it lints the code, not the token file.**

Three differentiators to defend:
1. **The resolver** — one allowed-set from any token source, resolved (aliases, modes, roles), shared by every surface and every host linter. Nobody else has a generic one; it's also the moat piece hardest to clone casually.
2. **Distance, not just exact match** — ΔE color matching and step-based length matching turn violations into one-keystroke fixes and make agent self-correction work; the ecosystem's ceiling today is exact-equivalence rewriting.
3. **Debt as a first-class number** — baseline compatible with ESLint/stylelint suppressions, SARIF fingerprints for new-only PR gates, and the suppression/arbitrary-value trend report no tool (OSS or commercial — including Omlet) produces.
